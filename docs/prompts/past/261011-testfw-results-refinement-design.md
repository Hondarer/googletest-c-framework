## 目的

- テスト定義の直前にサブ手順参照があっても、説明コメントをテスト項目の概要として出力します (BL-001 の解消)。

## テスト項目節

### 概要の収集

テスト定義 (`TEST`、`TEST_F`、`TEST_P`、`TYPED_TEST`) の直前に空行を挟まず書いた `//` コメントを、概要とします。  
テスト定義より前にあるサブ手順参照の行とその展開の範囲 (サブ手順展開の開始から終了まで) は、概要の収集を打ち切らず、読み飛ばします。

```cpp
// libcalc のエクスポート シンボル名が API 表と一致することの確認
// [サブ手順参照 名前=exportTest.SetUp]
TEST_F(exportTest, symbol_names_match)
```

CodeBlock: 概要が出力されるテスト ソース

この例のテスト項目節は、次のとおりです。

```markdown
## テスト項目

libcalc のエクスポート シンボル名が API 表と一致することの確認

### 状態

- サブ手順 exportTest.SetUp を実施する。
- CALC_EXPORT_TABLE から期待シンボル名一覧を構築する。
```

CodeBlock: 概要が出力されたテスト項目節

- 空行、サブ手順参照以外のタグを含むコメント、コメント以外の行は、現行どおりそれまでに集めた概要を破棄します。
- 正本文書には、説明コメントを先に、サブ手順参照を後に書く順序を規範として記載します。

### 状態節の空表示

状態節 (マルチ フェーズ テストの `状態_N` を含む) の本文が空の場合は、「特記すべき状態なし」と出力します。

```markdown
### 状態

特記すべき状態なし
```

CodeBlock: 空の状態節

手順節と確認内容節の本文が空の場合と、テスト項目節そのものが空の場合は、現行どおり「なし」と出力します。

## 日時の表記

結果ファイルに記載する日時は、すべて次の形式です。

```text
YYYY-MM-DD HH:MM:SS <時刻帯>
```

CodeBlock: 日時の形式

- 例: `2026-10-11 10:00:00 JST`
- 実行環境のローカル時刻とし、時刻帯は `date '+%Z'` の値です。値は `date '+%Y-%m-%d %H:%M:%S %Z'` で得ます。

## 個別結果 (results.md)

### 先頭のメタデータ

```text
# <テスト ID>

- 判定: <PASSED | WARNING | FAILED>
- 実施日時: <日時>
- 備考: `<コメント>`          ← コメントがある場合のみ
```

CodeBlock: 個別結果の先頭

- 「テスト バイナリ:」の行は出力しません (C/C++)。
- 実施日時は判定の直後に置きます。パラメーター テストのレコードのファイルも同じです。
- 実行結果節の実行コマンド (`./bin/<binary> --gtest_filter=<name>`) は現行どおりです。

### 実施日時の値

Table: 実施日時の値

| 言語 | 値 |
| --- | --- |
| C/C++ | そのテストのテスト バイナリを起動する直前に取得した時刻 |
| .NET | TRX のそのテスト結果の `startTime` 属性を、ローカル時刻に変換した値 |

- C/C++ でエビデンス生成に失敗したテストにも、起動直前に取得した時刻を記載します。
- .NET で `startTime` 属性がないテスト結果は、`dotnet test` の一括実行を開始した時刻を記載します。
- .NET の Theory のように、複数のテスト結果 (レコード) を 1 つの個別結果にまとめる場合は、`startTime` 属性を持つレコードのうち最も早い時刻を記載します。どのレコードにも `startTime` 属性がない場合は、一括実行を開始した時刻を記載します。
- .NET の変換は、C/C++ と同じ形式になるよう `date -d '<startTime>' '+%Y-%m-%d %H:%M:%S %Z'` で行います (GNU date は秒の小数と時刻帯のオフセットを解釈します)。

## 全体サマリー (summary.md)

先頭の「開始日時」を「実施日時」に改め、値を日時の表記の形式にします。値は全テストの開始時刻です。

```markdown
# <テスト ディレクトリ名> のテスト結果サマリー

- 実施日時: 2026-10-11 10:00:00 JST
```

CodeBlock: 全体サマリーの先頭

> コンソールに表示する `Test start on <LANG=C の date 出力>.` は変更しません。全体サマリーの値は、コンソールに表示しない別の記録 (サマリー用ジャーナルの行など) から取得します。

## プラットフォーム条件分岐 (C/C++)

### 対象マクロ

Table: プラットフォーム条件として評価するマクロ

| 実行環境 | 定義済みとして扱うマクロ |
| --- | --- |
| Windows | `PLATFORM_WINDOWS`、`_WIN32` |
| Linux | `PLATFORM_LINUX`、`__linux__` |

実行環境で定義済みとして扱わない対象マクロは、未定義として評価します。対象外のマクロ (`WIN32`、`_WIN64`、`linux`、`LINUX` など) を含む条件は、現行どおり未知の条件として分岐を除かずに出力します。

### 評価する書式

対象マクロ `X` の単独判定で、次の書式を評価します。

Table: 評価する書式

| 書式 | 真となる条件 |
| --- | --- |
| `#if defined(X)`、`#elif defined(X)` | `X` が定義済み |
| `#if !defined(X)`、`#elif !defined(X)` | `X` が未定義 |
| `#ifdef X` | `X` が定義済み |
| `#ifndef X` | `X` が未定義 |

```cpp
#ifndef _WIN32
    // Linux で出力するテスト コード
#else
    // Windows で出力するテスト コード
#endif
```

CodeBlock: 新たに評価される例

- 空白は、現行の `defined(X)` の判定と同じく、`#` の前後、ディレクティブ名の後、括弧の内側で許容します。`!` と `defined` の間の空白も許容します。
- `&&` または `||` を含む複合条件、条件式の後ろにコメントなどのトークンを置く書式は、評価しません。
- 評価規則はテスト本体 (`get_test_code_c_cpp.awk`) とサブ手順 (`test_subprocedures.py`) で同じです。
- 評価済みの分岐の除去、ディレクティブ行の除去、連続空行の圧縮は、現行の規則のままです。
