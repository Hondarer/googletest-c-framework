### 現行の出力の調査結果

Table: 現行の results 配下のテキスト ファイル

| ファイル | 生成元 | 現行の構成 |
| --- | --- | --- |
| `results/<TestId>/results.log` (C/C++) | `exec_test_c_cpp.sh` の `run_test`、`execute_test_case` | 1 行目 `Running test: <id> [# comment] on bin/<binary>`、`----` 区切りで テスト項目サマリー (`## テスト項目` 以下は Markdown)、テスト コード、実行コマンドと Google Test 出力 (ANSI 色を除去) |
| `results/<Suite>.<Test>/results.log` (C/C++ パラメーター テスト定義単位) | `gtest_summary_groups.py` | `Running test definition: <id>`、`----`、サマリー、定義コード、各レコードの results.log 全文を `## 実行レコード <name>` の後に連結 |
| `results/<TestId>/results.log` (.NET) | `exec_test_dotnet.sh`、`extract_dotnet_output.py` | C/C++ と同じ 3 ブロック構成。実行結果は `dotnet test` 出力の抜粋 |
| `results/all_tests/summary.log` | `exec_test_c_cpp.sh`、`exec_test_dotnet.sh` | 開始日時、`TEST_SRCS` の MD5 一覧、`<id>\t<PASSED/WARNING/FAILED>\t<comment>` の TSV 行、`Total tests` などの集計、警告行、`cobertura2gcovr.py` の固定幅カバレッジ表 |
| `results/**/<src>.gcov.txt` | `gcov`、`cobertura2gcov.py` | gcov 形式のテキスト |

現行の results.log には、Markdown として次の不整合があります。

- 1 行目の直後の `----` が setext 見出しの下線として解釈され、`Running test: ...` が H2 見出しになります。
- テスト コードと Google Test 出力がコード ブロックで囲まれていないため、`//` 行や `[==========]` 行が段落として整形されます。
- 文書の最上位見出し (H1) がなく、`## テスト項目` だけが見出しになっています。

利用箇所の調査結果:

- CI (`.github/workflows/ci.yml`) は `app/**/results/` をディレクトリ単位で成果物に登録しており、ファイル名に依存しません。
- `framework/testfw/bin_test/test_path_spaces.py`、`test_dotnet_path_spaces.py` が `results.log`、`summary.log` を名前で読み、内容を検査しています。
- 文書では `framework/testfw/docs/about-test-phase.md` の「テスト エビデンス (results.log)」節、`app/general/docs/dotnet-test-results-design.md`、`app/cplat/test/src/libcplatTest/prompt/TESTING.md` がファイル名と構成を記載しています。
- コンソールには、C/C++ では個別ファイルと同じ内容 (色付き) を `tee` で表示し、最後にテスト一覧、集計、バナーを表示しています。

## 現行の合意内容

ユーザーの依頼 (本対話、2026-10-10) により、次の内容は確定しています。

- testfw が生成する results のテキスト形式の結果を、完全な Markdown にします。
- テスト実行中のコンソール出力も、あわせて多少変化することを許容します。
- 仕様変更は本スキル (agree-before-generate) で合意してから実施し、計画ファイルは `prompt/` に置きます。

第 1 ターンの回答 (2026-10-10、Tetsuo Honda) により、次の内容が決まりました。

- 対象は個別結果、パラメーター テスト定義単位の結果、全体サマリー、gcov です。`results/` 配下を MkDocs や Pandoc で公開できる形にすることを意図します ([Q-001](#q-001-markdown-化の対象ファイル))。
- `results.md`、`summary.md` に改名し、旧 `.log` は出力しません ([Q-002](#q-002-結果ファイルの拡張子)、[Q-019](#q-019-旧形式-log-ファイルの併存))。
- 文字コードは UTF-8 に固定します ([Q-003](#q-003-結果ファイルの文字コード))。
- 個別結果は H1 をテスト ID とし、判定結果を記載し、`## テスト項目`、`## テスト コード`、`## 実行結果` の 3 節にします ([Q-004](#q-004-個別結果ファイルの見出し構成)、[Q-005](#q-005-個別結果ファイルへの判定結果の記載))。
- コード ブロックは動的なフェンス長と、`cpp` / `csharp` / `text` の言語指定を使います ([Q-006](#q-006-コード-ブロックのフェンス長)、[Q-007](#q-007-コード-ブロックの言語指定))。
- 空の節は「なし」と出力します ([Q-008](#q-008-空のサマリー節の表現))。
- パラメーター テスト定義単位のファイルは、レコードごとの見出し、判定、リンク、実行結果だけを収録します ([Q-009](#q-009-パラメーター-テスト定義単位ファイルへのレコードの収録方法))。
- 全体サマリーは、テスト一覧 (個別結果へのリンク付き)、MD5、カバレッジを Markdown 表にし、警告とエラーを admonition にします ([Q-010](#q-010-全体サマリーのテスト一覧の表現) 〜 [Q-014](#q-014-全体サマリー内の警告とエラーの表現))。
- コンソールは、個別テストの表示を Markdown 本文 (色付けは維持) にし、全テスト終了後の表示は現行を維持します ([Q-015](#q-015-個別テスト実行中のコンソール表示)、[Q-016](#q-016-全テスト終了後のコンソール表示))。
- .NET にも同じ構成を適用します ([Q-017](#q-017-net-の結果ファイルへの適用))。
- 更新文書は [Q-018](#q-018-更新する文書の範囲) の A〜E です。
- Markdown の形式検証は開発時の局所テストに限り、`make test` の実行時には行いません ([Q-020](#q-020-生成-markdown-の形式検証の方法))。
- 検証は `bin_test/` の全局所テストと全 app の `make test` を実行します ([Q-021](#q-021-局所検証の実施範囲))。

第 2 ターンの回答 (2026-10-10、Tetsuo Honda) により、次の内容が決まりました。

- gcov は `<src>.gcov.md` とし、H1、ソースのワークスペース相対パス、gcov 本文全体の `text` コード ブロックで構成します ([Q-022](#q-022-gcov-markdown-化後のファイル名)、[Q-023](#q-023-gcov-markdown-の構成))。
- `coverage.xml`、`coverage.json`、`lcov/` は現行のままとし、公開設定は今回の範囲に含めません ([Q-024](#q-024-機械可読ファイルと-html-の扱い)、[Q-025](#q-025-mkdocs-と-pandoc-による公開設定の範囲))。
- UTF-8 は BOM なしとし、変換できないバイト列は置換文字で続行します ([Q-026](#q-026-utf-8-の-bom-の有無)、[Q-027](#q-027-utf-8-へ変換できないバイト列の扱い))。
- `dotnet-test-results-design.md` は現行仕様の説明だけを更新し、過去の検証記録には注記を付けます。`framework/makefw/docs/subfolder-compilation.md` も更新します ([Q-028](#q-028-net-結果設計記録の過去の検証記録の扱い)、[Q-029](#q-029-makefw-の文書の更新))。

第 3 ターンの回答 (2026-10-10、Tetsuo Honda) により、次の内容が決まりました。

- パラメーター テスト定義単位のファイルの先頭に、全体サマリーと同じ規則で集約した総合判定と、レコード数、判定別の件数を記載します ([Q-030](#q-030-パラメーター-テスト定義単位ファイルへの総合判定の記載))。
- 各レコードのファイルには `## テスト項目` 節を設け、本文に定義単位のファイルへの相対リンクを置きます ([Q-031](#q-031-パラメーター-テストのレコード-ファイルのテスト項目節))。

第 2 ゲートの確認中に、ユーザーから全体サマリーの確認件数の集計について指摘がありました (2026-10-10)。版 1 の合意に含まれていない論点のため、[Q-032](#q-032-全体サマリーへの確認件数の集計) 〜 [Q-035](#q-035-全テスト終了後のコンソールへの確認件数の表示) を追加し、第 1 ゲートを再確認の対象に戻しました。

第 4 ターンの回答 (2026-10-10、Tetsuo Honda) により、次の内容が決まりました。

- 全体サマリーに `## 確認件数` 節を設け、テスト定義ごとの正常系、異常系、計と合計行を持つ表を記載します。テスト定義は結果ファイルへの相対リンク付きです ([Q-032](#q-032-全体サマリーへの確認件数の集計)、[Q-033](#q-033-全体サマリーの確認件数の表現))。
- 件数が確定しないテストは「未評価」とし、確定したテストだけを合計して、合計に含めていないテストの数を注記します ([Q-034](#q-034-未評価のテストを含む場合の確認件数の合計))。
- 確認件数は管理目的の情報としてファイルだけに記載し、コンソールには表示しません ([Q-035](#q-035-全テスト終了後のコンソールへの確認件数の表示))。
