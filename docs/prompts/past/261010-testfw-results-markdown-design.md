# testfw のテスト結果ファイルの Markdown 化 最終仕様

検討 ID: testfw-results-markdown-20261010

版: 2

状態: 承認済み (2026-10-10 Tetsuo Honda)

上流文書: `prompt/testfw-results-markdown-discussion.md` (版 2)

## 目的

`framework/testfw` が `make test` で `results/` 配下に出力する、人が読むための結果ファイルを、CommonMark と GitHub Flavored Markdown (GFM) に適合する Markdown にします。`results/` 配下を MkDocs や Pandoc でそのまま公開できる構造とし、ファイル間を相対リンクで辿れるようにします。

## 範囲

### 対象

Table: Markdown 化の対象と名前の対応

| 種別 | 現行のファイル | 変更後のファイル |
| --- | --- | --- |
| 個別結果 (C/C++、.NET) | `results/<TestId>/results.log` | `results/<TestId>/results.md` |
| パラメーター テスト定義単位の結果 (C/C++) | `results/<Suite>.<Test>/results.log` | `results/<Suite>.<Test>/results.md` |
| パラメーター テストのレコードの結果 (C/C++) | `results/<Suite>.<Test>/<Prefix>/<Param>/results.log` | `results/<Suite>.<Test>/<Prefix>/<Param>/results.md` |
| 全体サマリー (C/C++、.NET) | `results/all_tests/summary.log` | `results/all_tests/summary.md` |
| gcov (C/C++) | `results/<TestId>/<src>.gcov.txt`、`results/all_tests/<src>.gcov.txt` | `results/<TestId>/<src>.gcov.md`、`results/all_tests/<src>.gcov.md` |

旧名のファイル (`.log`、`.gcov.txt`) は出力しません。

### 対象外

- `results/all_tests/coverage.xml`、`results/all_tests/coverage.json`、`results/all_tests/lcov/` は、現行の形式と名前を維持します。
- `results/` を MkDocs や Pandoc で公開する設定 (`framework/docsfw` の変更) は行いません。
- 全テスト終了後のコンソール表示 (テスト一覧、集計、カバレッジ表、バナー) と、テスト開始前のコンソール表示 (開始日時、MD5 一覧、テスト件数) は変更しません。
- `make test` の実行時に、生成した Markdown の形式を検証する処理は組み込みません。

## 共通の出力規則

### 文字コードと改行

- すべての対象ファイルを、BOM なしの UTF-8、LF 改行で出力し、末尾を改行 1 つで終えます。
- 入力 (テスト コードの抜粋、テスト バイナリと `dotnet test` の出力、gcov の本文) は、ソース ファイルの文字コード指定 (`FILES_LANG`) で解釈してから UTF-8 に変換します。`utf8bom` の指定は BOM を除いて解釈します。
- テスト バイナリと `dotnet test` の出力、gcov の本文に、解釈できないバイト列がある場合は置換文字 (U+FFFD) に置き換えて続行し、判定には影響させません。
- テスト コードの抜粋を読み取れない場合は、現行どおりエビデンス生成の失敗としてテストを FAILED にします。
- コンソール表示は変換せず、現行どおり端末の文字コードで出力します。

### 見出しと空行

- 各ファイルの H1 は 1 つだけとし、ファイルの先頭に置きます。
- 見出しの前後、リスト、表、コード ブロック、admonition の前後に空行を 1 行置きます。
- コード ブロックの外で、空行を 2 行以上続けません。

### コード ブロック

- フェンスはバッククォートとし、内容中の最長のバッククォート連続より 1 つ長い長さ (最低 3) を動的に選びます。
- 言語指定は、C/C++ のテスト コードが `cpp`、C# のテスト コードが `csharp`、実行結果と gcov の本文が `text` です。
- 内容の末尾の空行は除き、内容が空の場合はコード ブロックの代わりに本文を「なし」とします。
- 実行結果からは ANSI エスケープ シーケンスを除去します (現行と同じ)。

### インライン要素

- テスト ID、テスト ディレクトリ名、ファイル パス、テスト バイナリのパスは、インライン コードにせず、そのまま記載します。Markdown の記法として解釈される文字 (`\`、`` ` ``、`*`、`[`、`]`、`<`、`>`、`&`、`~`、単語の境界にある `_`) だけをバックスラッシュでエスケープします。
- コメント (パラメーター テストの `# GetParam() = ...` など) と GTEST_FILTER の値は、インライン コードにします。内容にバッククォートがある場合は、内容中の最長の連続より長い区切りを使い、区切りと内容の間に空白を 1 つ入れます。
- 表のセル内の `|` は `\|` にエスケープします。
- 表には、表の直後に空行を挟んだ `Table:` 行でキャプションを付けます (docsfw の表のキャプションの規範)。キャプションは、MD5 表が「テスト対象ソースのファイル別の MD5 チェックサム」、テスト結果表が「テスト ID 別の判定と備考」、集計表が「判定別のテスト件数」、確認件数表が「テスト定義別の正常系と異常系の確認件数」、カバレッジ表が「ソース ファイル別の行とブランチのカバレッジ」です。
- 相対リンクのパスは、`/` 以外の予約文字と空白をパーセント エンコードします。

### 判定の表記

判定は、現行の全体サマリーと同じ `PASSED`、`WARNING`、`FAILED` の 3 値です。判定の規則 (Google Test の終了コード、`[ WARNING ]` 行の有無、エビデンス生成の失敗) は変更しません。

## 個別結果 (results.md)

### 構成

```text
# <テスト ID>

- 判定: <PASSED | WARNING | FAILED>
- テスト バイナリ: bin/<binary>          ← C/C++ のみ
- 備考: `<コメント>`                       ← コメントがある場合のみ

## テスト項目

<テスト項目サマリー>

## テスト コード

<テスト コードのコード ブロック>

## 実行結果

<実行コマンドと実行結果のコード ブロック>
```

### 先頭のメタデータ

- H1 はテスト ID です。パラメーター テストのレコードでは、現行の `Running test:` 行と同じ表示用 ID (`<Suite>.<Test>/<Prefix>/<Param>`) です。
- `テスト バイナリ` は現行の `on bin/<binary>` の値です。.NET では出力しません。
- `備考` は現行の `Running test:` 行の `# ...` 部分 (gtest のテスト一覧のコメント) です。

### テスト項目節

- 現行の `test_summary.py` が出力するテスト項目サマリーの見出し `## テスト項目` を、この節の見出しとして使います。概要、`### 状態`、`### 手順`、`### 確認内容 (...)`、マルチ フェーズ テストの `_N` 付き見出しと `### 確認件数合計 (...)` は現行どおりです。
- `### 状態`、`### 手順`、`### 確認内容` の本文が空の場合は、本文に「なし」と出力します。
- テスト項目サマリーを生成しない場合 (概要とタグがないテスト) は、節の本文を「なし」とします。
- 現行のサマリー末尾の区切り `----` は出力しません。

> [!NOTE]
> `### 確認件数合計 (...)` は見出しの括弧内に集計値を持つ節で、本文はありません。この節には「なし」を出力しません。

### テスト コード節

現行のテスト コード ブロックの内容 (テスト本体、パラメーター テストの `INSTANTIATE_TEST_SUITE_P`、サブ手順の定義) を、1 つのコード ブロックに入れます。

### 実行結果節

- C/C++ では、1 行目を現行の実行コマンド (`./bin/<binary> --gtest_filter=<name>`) とし、続けて Google Test の出力、シグナルや終了コードによる失敗の行を入れます。
- .NET では、`extract_dotnet_output.py` の現行の出力 (`dotnet test --filter ...` の行を含む) を入れます。

### エビデンス生成の失敗

テスト項目サマリーまたはテスト コードの抽出に失敗した場合は、判定を FAILED とし、`## テスト項目` の本文にエラー メッセージを `> [!CAUTION]` の admonition で出力します。`## テスト コード` と `## 実行結果` の本文は、得られた内容があればコード ブロック、なければ「なし」とします。

## パラメーター テスト (C/C++)

### 定義単位のファイル

```text
# <Suite>.<Test>

- 総合判定: <PASSED | WARNING | FAILED>
- 実行レコード数: <n> (PASSED: <a>, WARNING: <b>, FAILED: <c>)   ← 0 件の判定は省略

## テスト項目

<テスト定義のテスト項目サマリー>

## テスト コード

<テスト定義のコード ブロック>

## 実行レコード

### <レコードのテスト ID>

- 判定: <PASSED | WARNING | FAILED>
- 詳細: [results.md](<Prefix>/<Param>/results.md)

<実行結果のコード ブロック>

### <次のレコード>
...
```

- 総合判定は、全体サマリーと同じ規則 (FAILED が 1 件でもあれば FAILED、FAILED がなく WARNING があれば WARNING、それ以外は PASSED) で、実行したレコードの判定を集約します。
- フィルターで一部のレコードだけを実行した場合は、`実行レコード数` の後ろに全レコード数を `/ <m>` の形で併記します。テスト項目サマリーの件数は、現行どおり「未評価」になります。
- レコードの見出しは、現行の `## 実行レコード <name>` の `<name>` (Google Test のテスト名) です。
- 各レコードの節には、レコードのファイルのうち実行結果のコード ブロックだけを収録し、テスト コードは重複させません。
- 定義単位のファイルは、全レコードの実行が終わった時点で書き出します。テスト定義の解析は、現行どおり全レコードの実行前に行い、失敗した場合はテストを開始しません。

### レコードのファイル

個別結果と同じ構成です。`## テスト項目` の本文は、定義単位のファイルへの相対リンクだけとします。全体件数は重複掲載しません。

```markdown
## テスト項目

テスト項目は [テスト定義の結果](../../results.md) を参照してください。
```

## 全体サマリー (summary.md)

### 構成

```text
# <テスト ディレクトリ名> のテスト結果サマリー

- 開始日時: <現行と同じ LANG=C の date 出力>

> [!NOTE]                                       ← GTEST_FILTER の指定時のみ
> GTEST_FILTER = `<値>`

## テスト対象ソースの MD5                        ← C/C++ で TEST_SRCS がある場合のみ

| MD5 | ファイル |

## テスト結果

| テスト ID | 結果 | 備考 |

## 集計

| 項目 | 件数 |

## 確認件数

| テスト定義 | 正常系 | 異常系 | 計 |

## 警告とエラー                                  ← 該当がある場合のみ

## カバレッジ                                    ← C/C++ でカバレッジ表を生成した場合のみ

| File | Lines | Exec | Cover | Branch | BrCov | Missing |
```

### 各節

- テスト ディレクトリ名は、`make test` を実行した末端ディレクトリの名前 (C/C++ ではテスト バイナリ名と同じ) です。
- `テスト対象ソースの MD5` の表は、現行の行と同じ順序で、MD5 とワークスペース相対パスを出力します。
- `テスト結果` の表は、現行の TSV 行と同じ順序で、テスト ID (個別結果への相対リンク付き)、判定、備考を出力します。リンク先は `../<テスト ID>/results.md` です。備考がない場合は空欄とします。
- `集計` の表の項目は、現行と同じ `Total tests`、`Passed`、`Warning(s)`、`Failed` です。フィルター実行時は、`Total tests` の件数の後ろに現行と同じ `(filtered, <GTEST_FILTER>)` を併記します。
- `確認件数` の表は、「確認件数」節の規則に従います。
- `カバレッジ` の表は、`cobertura2gcovr.py` の Markdown 出力で、列と行の並び、`TOTAL` 行の内容は現行の固定幅の表と同じです。

### 確認件数

テスト ディレクトリ全体の確認タグ (`[確認_*]`、`[Pre-Assert確認_*]`) の確認件数を、テスト定義ごとと合計で、分類 (正常系、異常系) 別に記載します。確認件数は管理目的の情報で、コンソールには表示しません。

```markdown
## 確認件数

| テスト定義 | 正常系 | 異常系 | 計 |
| --- | ---: | ---: | ---: |
| [sampleCloseTest.handle_null](../sampleCloseTest.handle_null/results.md) | 0 | 2 | 2 |
| [tcp_allocation_failure_test.releases_buffers_and_reopens_endpoints](../tcp_allocation_failure_test.releases_buffers_and_reopens_endpoints/results.md) | 66 | 36 | 102 |
| 合計 | 66 | 38 | 104 |
```

- 件数は、各テストの結果ファイルのテスト項目サマリーと同じ計算結果です。`[状態確認]` は計上せず、回数式とサブ手順の参照回数を反映します。
- 行の単位はテスト定義です。通常テストは 1 テストで 1 行、C/C++ のパラメーター テストは定義単位で 1 行 (リンク先は定義単位のファイル)、.NET はメソッド単位で 1 行です。パラメーター テストのレコードごとの行は設けません。
- 行の順序は、`テスト結果` の表で各テスト定義が最初に現れる順です。
- 確認タグがないテスト定義も、件数 0 の行として含めます。
- 次のテスト定義は、正常系、異常系、計の欄を「未評価」とし、合計に含めません。
    - テスト項目サマリーの生成に失敗したテスト
    - `GTEST_FILTER` で一部のレコードだけを実行したパラメーター テスト
- 「未評価」のテスト定義がある場合は、表の下に「合計には、未評価のテスト定義 <n> 件を含みません。」と注記します。
- テスト定義が 1 件もない場合は、本文を「なし」とします。

> [!NOTE]
> 実行スクリプトが件数を得るため、テスト項目サマリーを生成する処理 (`test_summary.py`、`test_subprocedures.py`、`gtest_summary_groups.py`) は、Markdown の本文とは別に、テスト定義ごとの分類別の件数を機械可読な形で実行スクリプトへ渡します。

### 警告とエラー

- 警告 (現行の `[ WARNING ]` 行) は `> [!WARNING]`、エラー (現行の `Error:` 行と `[  FAILED  ]` 行) は `> [!CAUTION]` の admonition とし、1 件ごとに 1 つの admonition にします。
- テストの実行中に発生した警告とエラーには、対象のテスト ID を admonition の本文に含めます。
- 複数行の詳細 (gcovr のエラー出力など) は、admonition 内の `text` コード ブロックにします。
- テスト開始前に処理を中止するエラー (テスト バイナリがない、MD5 を計算できない、テスト一覧を取得できない) の場合も、その時点までの内容と `警告とエラー` 節を持つ summary.md を書き出します。

> [!NOTE]
> Markdown の表は途中に別の要素を挟めないため、全体サマリーは現行のような逐次追記ではなく、テストの実行中に記録した内容から最後に一括で書き出します。コンソールの警告とエラーの表示は、現行どおり発生時に色付きの 1 行で出力します。

## gcov (<src>.gcov.md)

```text
# <ソース ファイル名> のカバレッジ

- ソース: <ワークスペース相対パス>

<gcov 本文全体の text コード ブロック>
```

- ソース ファイル名とパスは、gcov 本文の `0:Source:` 行から求めます。パスがワークスペースの配下にある場合はワークスペース相対パスとし、それ以外は記載どおりとします。
- gcov 本文は変更せずに収録します。

## コンソール表示

個別テストの実行中は、個別結果ファイルと同じ Markdown 本文を表示し、Google Test と `dotnet test` の出力の色付けを維持します。ただし、次の 2 点はファイルと異なります。

- `判定` の行は、テストの実行前には確定しないため、コンソールには表示しません。判定は、実行結果と全テスト終了後の一覧で確認します。
- 実行結果のコード ブロックは、出力を逐次表示するため、フェンスの長さを 3 に固定します。

> [!NOTE]
> Windows の色付け (`add_gtest_color.py`) は行頭の `[` で始まる Google Test の見出しだけを対象とするため、Markdown の見出しやフェンスの行は色付けされません。色付けの規則は変更しません。

## 検証

1. `framework/testfw/bin_test/` の全局所テストを実行し、成功することを確認します。
2. 全 app の `make test` を、同時に 1 本ずつ実行し、成功することと、内容のある `.warn` がないことを確認します。
3. 代表的な結果ファイル (通常テスト、パラメーター テストの定義単位とレコード、サブ手順を含むテスト、.NET、全体サマリー、gcov) に `text_style_jp.py --dry-run` を参考として実行し、指摘内容を報告します。差分がないことは合格の条件にしません。

## 受入条件

1. `make test` が対象の Markdown ファイルを出力し、旧名のファイルを出力しないこと。
