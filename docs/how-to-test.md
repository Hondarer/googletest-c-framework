# How to test

## 単体テストのソース ファイルを指定する方法

単体テストの `makepart.mk` では、テストで動作を確認し、カバレッジを充足する対象のソース ファイルだけを `TEST_SRCS` に指定します。テスト対象のリンクを成立させる依存実装やテスト固有の補助実装など、カバレッジ対象にしないソース ファイルは `ADD_SRCS` に指定します。

`TEST_SRCS` はテスト用コンパイル フラグと override ヘッダーによる関数置換の対象になりますが、`ADD_SRCS` はこれらの対象になりません。ファイルが `prod/` 配下にあるかどうかではなく、そのテストでの役割に基づいて選択します。

`TEST_SRCS` と `ADD_SRCS` は、いずれもテスト ディレクトリの外にあるソース ファイルを引き込むための指定です。
テスト ディレクトリ直下に置いたソース ファイルは自動的にコンパイル対象となるため、`ADD_SRCS` へ記載する必要はありません。
テスト固有の fake やスタブをテスト ディレクトリへ直接置く場合は、`makepart.mk` に何も追加しません。

> [!NOTE]
> 自動収集の対象は、テスト ディレクトリ直下の `*.c` / `*.cc` / `*.cpp` です (`makefw/makefiles/_collect_srcs.mk`)。
> カバレッジの集計対象は `TEST_SRCS` に指定したファイルだけであるため、自動収集されたテスト用の補助ソースがカバレッジへ混入することはありません。

詳細は [makepart.mk / makechild.mk / makelocal.mk の役割と使い分け](../../makefw/docs/makeparts.md#test_srcs-と-add_srcs-の留意事項) を参照してください。

## カバレッジの基準

ホワイトボックス テストが充足すべきカバレッジは、原則として条件網羅 (C2) とします。
判定を構成する各条件が、真と偽の両方を取ることを確認してください。命令網羅 (C0) の充足をもって完了としません。

```c
if (buffer == NULL || buffer_size == 0u || text == NULL)
```

この判定は 1 行ですが、条件は 3 つあります。命令網羅では入力を 1 つ与えるだけで充足しますが、条件網羅では 3 つの条件それぞれが真になる入力と、すべてが偽になる入力が必要です。

### 計測は Linux を正本とする

条件網羅の充足確認は Linux (gcov / gcovr) を正本とします。Windows では行網羅のみを確認します。

GCC は短絡評価の論理演算子を条件ごとの分岐へ展開するため、gcov の分岐情報は判定網羅 (C1) ではなく条件網羅に対応します。
ただし、各条件が独立して結果に影響することまでは確認しないため、MC/DC の充足は判定できません。

Windows の計測に使う OpenCppCoverage は行カバレッジのみを提供し、分岐と条件は計測しません。
生成される Cobertura XML には分岐情報が含まれないため、Windows で `make test` を実行しても条件網羅は判定できません。

参考: [OpenCppCoverage の Features](https://github.com/OpenCppCoverage/OpenCppCoverage#features)

> [!WARNING]
> 分岐情報を持たない Cobertura XML では、集計時に `branch-rate` が `1.0` に設定されます (`bin/cobertura_merge.py`)。
> これは分岐を 100% 網羅したことを意味せず、分岐を計測していないことを意味します。Windows で生成した XML の `branch-rate` を網羅率として読まないでください。

### 到達できない条件への対処

到達できない条件が残った場合は、次の順で対処してください。

1. 公開 API 経由で到達できないファイル内の `static` 関数は、inject 機能でアクセサーを通して到達させる
2. 実行環境の都合で到達できない依存関数の失敗経路は、モックで失敗を注入して到達させる
3. それでも到達できない条件は、到達できない理由をテスト コードにコメントとして残す

> [!NOTE]
> 条件網羅を基準にするのは、C の防御的な入力検証が `||` で連結された複合条件に集約されやすいためです。
> 命令網羅を基準にすると、複合条件のうち 1 つの条件しか検証していないテストが、指標の上では完了として扱われます。

## テストの構成単位

本フレームワークは、テスト対象のソース ファイル 1 本に対してホワイトボックス テスト 1 本を対応させる設計です。
`TEST_SRCS` に対象ソースを 1 本だけ指定し、依存を override ヘッダーでモックへ差し替えることで、ファイル内に閉じた `static` 関数を含む全分岐へ到達できます。

この対応関係を保つため、以下に従ってください。

### ソース 1 本につきテスト ディレクトリは 1 つとする

同一のソース ファイルを、複数のテスト ディレクトリの `TEST_SRCS` に指定しません。
対象関数が多いソースを分割してテストしたい場合は、テスト ディレクトリを分けるのではなく、1 つのテスト ディレクトリ内でテスト ファイルを分割し、`makepart.mk` の `TEST_SRCS` は 1 本に保ちます。

> [!NOTE]
> カバレッジはテスト ディレクトリ単位で集計されます。同一ソースを複数のテスト ディレクトリで `TEST_SRCS` に指定すると、そのソースがディレクトリの数だけ重複計上されます。
> 各エントリは互いの到達行を知らないため、実際には全分岐を網羅していても、集計上は低いカバレッジが対象ソースの数だけ並ぶことになります。

### ディレクトリ名を対象ソースに一致させる

テスト ディレクトリ名は、対象ソースのファイル名を lowerCamelCase 化して `Test` を付けた名前とします。
対象ソースが担う代表的な関数名や機能名をディレクトリ名にしません。同じソースを対象とするテストが分裂する原因になります。

### テスト ファイルとスイート名を一致させる

1 つのテスト ディレクトリ内では、テスト対象の関数ごとにテスト ファイルを分けられます。
ディレクトリ内のすべての `.cc` がビルド対象になるため、`makepart.mk` の変更は不要です。

テスト ファイル名とスイート名 (`TEST_F` の第 1 引数) は一致させ、1 ファイルに 1 スイートだけを置きます。
対象関数が少なくファイルを分ける必要がない場合は、ディレクトリ名と同じ名前のファイル 1 本にします。

```text
prod/libsrc/sample/sample_name.c
    -> test/src/libsampleTest/sampleNameTest/
       +- sampleFooTest.cc   TEST_F(sampleFooTest, ...)
       +- sampleBarTest.cc   TEST_F(sampleBarTest, ...)
```

分割した場合も `TEST_SRCS` は対象ソース 1 本のままです。カバレッジはディレクトリ単位で集計されるため、分割によって重複計上は発生しません。

### テスト関数名に test_ 接頭辞を付けない

`TEST`、`TEST_F`、`TEST_P` のマクロ自体がテストであることを示しているため、テスト関数名の `test_` は冗長です。

### ホワイトボックス テストで実ライブラリをリンクしない

依存の差し替えは `LIBS += mock_<lib> mock_libc` で行います。
テスト対象と同じライブラリの実体 (`LIBS += <lib>`) を指定しません。

> [!NOTE]
> 実ライブラリをリンクすると、対象ソースが呼び出す依存関数がモックへ差し替わらず本物へ解決されます。
> その結果、メモリ確保の失敗や書き込みエラーといった異常系の分岐へ到達できず、対象ソースの残り分岐が恒久的に未到達のまま残ります。

必要なモックが不足している場合は、実ライブラリをリンクして回避せず、モックを追加してください。
モックの追加方法は [how-to-mock.md](how-to-mock.md) と [mock-injection-technique.md](mock-injection-technique.md) を参照してください。

### TEST_SRCS を空にしない

`TEST_SRCS` が空のテストは、リンクした実ライブラリに対する黒箱テストになります。
このとき、実際に動作を確認したソース ファイルはカバレッジの帰属先を持たず、計測から漏れます。

例外は、ライブラリ全体を対象とする検査 (公開シンボル表の照合など) に限ります。
この場合は、`TEST_SRCS` を空にしている理由を `makepart.mk` にコメントとして残してください。

### ファイル内に閉じた関数は inject で到達させる

`static` 関数のうち、公開 API 経由では到達できない分岐 (呼び出し元がすべて事前に引数を検証している防御的なガードなど) は、inject 機能でテストします。

テスト ディレクトリに `<対象ソース名>.inject.c` を置くと、ビルド時に対象ソースの末尾へ `#include` として結合されます。
結合されたコードは対象ソースと同じ翻訳単位に入るため、`static` 関数や `static` 変数へ直接アクセスできます。
テスト コードから呼び出すためのアクセサーを `.inject.c` に定義し、その宣言を `<対象ソース名>.inject.h` に置きます。

規範例は `app/tutorial/test/src/static-access/` です。ファイルの引き込み方法 (シンボリック リンクとコピーの切り替え) は [makeparts.md](../../makefw/docs/makeparts.md) を参照してください。

> [!NOTE]
> inject ファイルを置くと、対象ソースはシンボリック リンクではなくコピーで引き込まれます。
> 以前に inject なしでビルドした痕跡が残っている場合はシンボリック リンクのままとなり、コピーに失敗します。この場合はビルド ディレクトリの当該ファイルを削除してから再実行してください。

> [!NOTE]
> `.inject.c` / `.inject.cc` はビルド フレームワーク (`framework/makefw`) が単独コンパイル対象から除外するため、ビルド時に警告は発生しません。
> ただし IntelliSense (VS Code の C/C++ 拡張など) は `.inject.c` を単体のファイルとして解析するため、`#ifndef _IN_TEST_SRC` で対象ソースを自己インクルードするガード (規範例参照) は編集時の識別子解決のために必要です。

### 統合テストは TEST_SRCS を宣言しない

複数のコンポーネントを実際にリンクして動作を検証する統合テストは、カバレッジの充足を目的としません。
必要なソース ファイルは `ADD_SRCS` に指定するか、実ライブラリをリンクします。

> [!NOTE]
> 統合テストが `TEST_SRCS` を宣言すると、その中の各ソースは単体テスト側と重複計上されます。
> 統合テストは限られた経路しか通らないため、生成されるエントリは軒並み低いカバレッジになり、集計値を実態から乖離させます。

## 個別のテストを行う方法

主にデバッグ時に、個別のテストを行う方法について説明します。

### テスト対象フォルダーにて make test

テスト対象フォルダーにて `make test` すれば、コンパイルとテストが実行されます。

### make test にフィルター文字列を指定

`make test` を呼び出す際にフィルター文字列を指定し、任意のテストのみ行うことができます。

参考: [google test のオプションを使ってみた](https://country-programmer.dfkp.info/2021/05/re_google_test_003/)

```bash
make test GTEST_FILTER=*call_times_check_with_args*
```

あるいは、`GTEST_FILTER` 環境変数にフィルター文字列を指定します。

```bash
export GTEST_FILTER=*call_times_check_with_args*
make test
...
export -n GTEST_FILTER # フィルター不要になったら、GTEST_FILTER 環境変数を削除
```

### 再テストのスキップ

テスト対象フォルダー (leaf ディレクトリ) 単位で、`TEST_SRCS`・`ADD_SRCS`・ローカルの `makepart.mk`/`makelocal.mk` の MD5 が
前回のクリーンな成功時 (`Failed` が 0 件) から変化していない場合、`make test` は実際のテスト実行を省略します。  
スキップした場合は `results/` 以下を前回のまま残し、以下を表示します。

```text
INFO: Skipping test (dependencies are unchanged and clean)
```

判定用のシグネチャは、テスト対象フォルダー直下の `test.stamp` に保存されます。  
`GTEST_FILTER` を指定した実行は、テスト対象の一部のみを検証したものであり「クリーンな全件成功」の証拠にならないため、
スキップ判定にもスタンプの更新にも使われません。

`MAKEFW_TEST_FORCE=1` を指定すると、スタンプの内容に関わらず必ずテストを実行します。

```bash
MAKEFW_TEST_FORCE=1 make test
```

この仕組みは `app/<name>/makefile` の `test:` ターゲットが持つ app 単位のスキップ (`make_test.stamp`) とは独立しています。  
app 単位のスキップは、途中で 1 つでもテストが失敗すると `make_test.stamp` が更新されないため全 leaf の再実行に戻りますが、
leaf 単位の `test.stamp` はテスト対象フォルダーごとに個別に維持されるため、失敗箇所を修正した後の再実行では、
変更されていない leaf だけが引き続きスキップされます。
