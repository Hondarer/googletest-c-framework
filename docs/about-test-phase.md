# テスト コードの各フェーズについての解説

テスト コードは、4 つの必須フェーズと任意の Cleanup フェーズに分けて記載します。

本テスト フレームワークには、次に述べる各フェーズのコメントからテスト エビデンスを生成する機能があります。

それぞれのフェーズの目的と具体的な内容について説明します。

- `TEST`、`TEST_F`、`TEST_P` などのテスト本体では、`{` の次の非空行を `// Arrange` とします。
- ローカル変数の宣言、モック オブジェクトの生成、テスト データや設定の準備は、すべて `// Arrange` より後に記載します。
- `[状態]` タグは、Arrange フェーズの内容をテスト エビデンスへ出力する場合に使用します。
- `[状態確認]` タグは、テスト対象の振る舞いの確認に直接寄与しない確認 (準備した資源の確認、結果を取り出す補助の関数の成否など) に使用します。被テスト関数の振る舞いを判定する `[確認_*]` とは区別します。
- `[状態]` タグを付けない場合も `// Arrange` は省略しません。

## Arrange フェーズ [状態] [状態確認]

### 目的

このフェーズでは、テスト対象のオブジェクトや依存関係を準備し、テストを実行するための初期状態と前提条件を設定します。

### 内容

- テスト対象のオブジェクトをインスタンス化します。
- 必要なモック オブジェクトを作成します。
- テスト データを準備します。
- モックの既定動作 (`ON_CALL` / `WillByDefault`) を設定します。

`ON_CALL` は呼び出されたときの既定動作であり、呼ばれること自体は検証しません。依存オブジェクトの初期設定なので Arrange に置き、`[状態]` で説明します。

```cpp
ON_CALL(mock_sys_file, flock(_, _, _, _, _))
    .WillByDefault(Return(0)); // [状態] - flock() から 0 を返すように既定動作を設定する。
```

`ON_CALL` に `[状態確認]` や `[Pre-Assert確認_*]` / `[Pre-Assert手順]` は使いません。`[状態確認]` は現在の値を ASSERT/EXPECT で確かめるためのタグです。既定動作を `[Pre-Assert手順]` に書くと、Act 用の `WillOnce` と同じ `### 手順` に並び、既定値と注入値が矛盾して解釈されるおそれがあります。

### 例

```cpp
// Arrange
// テスト対象のクラス
MyClass myObject;

// モック オブジェクトの作成
MockDependency mockDependency;
ON_CALL(mockDependency, SomeMethod()).WillByDefault(Return(false)); // [状態] - SomeMethod() から false を返すように既定動作を設定する。
```

### 資源確認 [状態確認]

テスト対象の振る舞いの確認に直接寄与しない確認には、`[状態確認]` タグを使用します。

- 被テスト関数は、テスト名とテスト関数の前の「〜ことの確認」が示す関数です。テスト内のヘルパー関数を通して呼ぶ場合も含みます。
- 被テスト関数の戻り値、出力、呼び出しによる状態の変化の判定は `[確認_*]` とします。
- それ以外の関数 (準備や結果の取り出しに使う補助の関数、ファイル操作、テスト用ヘルパー) の成否や、準備した資源の判定は `[状態確認]` とします。
- `[状態確認]` は Arrange フェーズと Act フェーズで使用し、Pre-Assert フェーズや Assert フェーズでは使用しません。Assert フェーズには被テスト関数の判定だけを置きます。
- `_正常系`/`_異常系` のサフィックスは付けません。
- `### 確認` セクションの先頭に、出現順に `- (説明文)` の形式 (括弧で囲む) で出力されます。Act の実行結果を検証する `[確認_*]` とは異なり、確認件数 (`正常系:n1, 異常系:n2` など) には計上されません。
- 説明文は `[確認_*]` と同じく、マクロが行う判定を書きます ([確認コメントの書き方](#確認コメントの書き方))。
- 総合期待は書きません。`### 確認` セクションでは説明文全体が括弧で囲まれるため、総合期待の括弧が入れ子になります。準備した内容は `[状態]` に書きます。

準備の呼び出しと成否確認が別行なら、行ごとにタグを分けます。

```cpp
// Arrange
char *buffer = (char *)malloc(16); // [状態] - 16 バイトのバッファーを確保する。
ASSERT_NE(nullptr, buffer); // [状態確認] - buffer が nullptr 以外であること。
```

1 行の `ASSERT_*` / `EXPECT_*` が準備と確認を兼ねるときは、`EXPECT_CALL` に `[Pre-Assert確認_*]` と `[Pre-Assert手順]` を並べるのと同じく、`[状態]` と `[状態確認]` の両方を付けます。`[状態確認]` だけでは、何を用意したかが `### 状態` に残りません。

```cpp
ASSERT_EQ(0, pipe(pipe_fds)); // [状態] - パイプを生成する。
                              // [状態確認] - pipe() の戻り値が 0 であること。
```

## Pre-Assert フェーズ [Pre-Assert確認_*] [Pre-Assert手順]

### 目的

Act フェーズを実施する際の各モックへの呼び出しの期待を設定し、必要に応じて戻り値も制御します。`EXPECT_CALL` はこのフェーズに置きます。`ON_CALL` は既定動作の準備なので Arrange に置きます。

### 内容

- モック オブジェクトへの呼び出し回数や順序を確認します。
- `EXPECT_CALL` の `WillOnce` / `WillRepeatedly` で、呼び出された場合の戻り値を設定します。

### タグ

| タグ | 用途 |
|-----|------|
| `[Pre-Assert確認_正常系]` | 呼び出し期待の検証 (正常な動作パス) |
| `[Pre-Assert確認_異常系]` | 呼び出し期待の検証 (エラー処理パス) |
| `[Pre-Assert手順]` | 呼び出された場合の動作 |

Table: Pre-Assert フェーズの検証タグ一覧

確認と手順は役割で分離して記載します。

- 呼び出されること、呼び出されないこと、呼び出される回数、引数の内容の検証は `[Pre-Assert確認_正常系]` / `[Pre-Assert確認_異常系]` に記載します。
- 呼び出された場合に戻り値を返す、出力引数や変数を操作する動作 (`WillOnce` / `WillRepeatedly` の中身) は `[Pre-Assert手順]` に記載します。
- 1 つの `EXPECT_CALL` に付ける説明は、`[Pre-Assert確認_*]` を先に、`[Pre-Assert手順]` を後に書きます。`### 確認` と `### 手順` は別のセクションに出力されるため順序は出力に影響しませんが、テスト コード上で「〜が呼び出されることを確認し、〜を返す」と読めるようにするためです。

- モックのコールバック内に置く `ASSERT_*` / `EXPECT_*` にも、`[Pre-Assert確認_*]` を付けます。
- `[Pre-Assert確認_*]` が `WillOnce` の動作 (手順) を説明している場合は、確認を呼び出し回数の判定に直し、動作の説明を `[Pre-Assert手順]` として記載します。

`[Pre-Assert確認_*]` の説明文には、[確認コメントの書き方](#確認コメントの書き方) に従い、呼び出しの回数と引数の条件を判定として書きます。

| 指定 | 判定の書き方 |
| --- | --- |
| `.Times(0)` | f() が呼び出されないこと。 |
| `.Times(0)` で引数条件あり | X を指定した f() の呼び出しがないこと。 |
| `.Times(n)`、または `WillOnce` が n 個で `WillRepeatedly` なし | f() が n 回呼び出されること。 |
| `.Times(AtLeast(n))`、または `WillOnce` が n 個で `WillRepeatedly` あり | f() が n 回以上呼び出されること。 |
| `.Times(AnyNumber())`、または `WillRepeatedly` だけ | f() が任意の回数呼び出されること。 |

Table: 呼び出し回数の書き方

`_` (任意の値) 以外の引数条件は、「X を指定して」の形で列挙します。GoogleMock のマッチャーで指定した引数は、意味を日本語で書きます。

| マッチャー | 日本語 |
| --- | --- |
| `StrEq(x)` | x と等しい文字列 |
| `HasSubstr(x)` | x を含む文字列 |
| `NotNull()` | nullptr 以外 |
| `Pointee(x)` | 指す先が x であるポインター |

Table: マッチャーの言い換え

表にないマッチャーも、同じ考え方で判定の意味を日本語で書きます。

引数条件付きの `.Times(0)` は、否定が呼び出しだけにかかるよう、引数条件を呼び出しの修飾として前に置きます。

```cpp
EXPECT_CALL(mock_cplat_, cplat_fopen(StrEq("/tmp/output.bin"), StrEq("wb"), _))
    .Times(0); // [Pre-Assert確認_異常系] - "/tmp/output.bin" と等しい文字列、"wb" と等しい文字列を指定した cplat_fopen() の呼び出しがないこと。
```

```cpp
EXPECT_CALL(mock_cplat_, cplat_fopen(StrEq(path), StrEq("rb"), nullptr))
    .WillOnce(Return(file_)); // [Pre-Assert確認_正常系] - cplat_fopen() が path と等しい文字列、"rb" と等しい文字列、nullptr を指定して 1 回呼び出されること。
                              // [Pre-Assert手順] - cplat_fopen() から設定ファイルを開くハンドルを返す。
```

### 例

```cpp
// モック メソッドが呼び出されたとき true を返すことを期待
EXPECT_CALL(mockDependency, SomeMethod())
    .WillOnce(Return(true)); // [Pre-Assert確認_正常系] - SomeMethod() が 1 回呼び出されること。
                             // [Pre-Assert手順] - SomeMethod() から true を返す。
```

### 動作を注入しない呼び出しの期待

`WillOnce` / `WillRepeatedly` に `DoDefault()` だけを渡す `EXPECT_CALL` は、動作の指定をやめ、`.Times(n)` で呼び出し回数を書きます。動作を注入しないため、`[Pre-Assert手順]` は書きません。

```cpp
EXPECT_CALL(mock_stdio, printf(_, _, _, StrEq("3\n")))
    .Times(1); // [Pre-Assert確認_正常系] - printf() が "3\n" と等しい文字列を指定して 1 回呼び出されること。
```

`DoDefault()` と別の動作を組み合わせる `EXPECT_CALL` (1 回目は失敗を返し、2 回目は既定の動作など) は、注入する動作を `[Pre-Assert手順]` に書きます。

> [!NOTE]
> 既定の動作を `[Pre-Assert手順]` に書くと、`ON_CALL` と同じく、注入した値と既定の値が `### 手順` に並び、矛盾して読まれるおそれがあります。`DoDefault()` だけの指定は回数の期待と同じ意味のため、回数で書きます。

### 呼び出しの順序に依存する期待

1 回目の呼び出しでは許し、2 回目の呼び出しでは禁じる期待のように、Act の途中で設定が必要な `EXPECT_CALL` は、[マルチ フェーズ テスト](#マルチ-フェーズ-テスト) に分け、2 回目の Act の前の Pre-Assert に置きます。間の Assert に判定がない場合は、構造コメントだけを置きます。

```cpp
// Act
(void)format_job_failed(&actual_matched); // [手順] - 壊れた公開内容で組み立てる。

// Assert

// Pre-Assert_2
EXPECT_CALL(mock_cplat, cplat_local_lock_try_lock(_))
    .Times(0); // [Pre-Assert確認_異常系] - cplat_local_lock_try_lock() が呼び出されないこと。(同じ公開内容の取り込みを試みないことの確認)

// Act_2
(void)format_job_failed(&actual_matched); // [手順] - もう一度組み立てる。

// Assert_2
EXPECT_NE(0, actual_matched); // [確認_異常系] - actual_matched が 0 以外であること。(以前の条件を維持したことの確認)
```

## Act フェーズ [手順]

### 目的

このフェーズでは、Arrange フェーズで準備した状態をもとに、テスト対象のメソッドや機能を実行して戻り値を得ます。

### 内容

- テスト対象のメソッドを呼び出します。

被テスト関数の戻り値は変数で受け、Assert フェーズではその変数を検証します。被テスト関数の呼び出しを `EXPECT_*` / `ASSERT_*` の引数に直接書きません。

### 例

```cpp
// テスト対象のメソッドを呼び出す
bool result = myObject.TestedMethod(); // [手順] - TestedMethod() を呼び出す。
```

### Act の中の判定

Act フェーズの中に `EXPECT_*` は置きません。Assert フェーズへ移し、関数呼び出しを直接判定している場合は戻り値を変数で受けます。ループの中の判定は、反復ごとの値を配列などに残して Assert で確かめます。

Act フェーズの中の `ASSERT_*` は、判定の種類と後続の手順で扱いを分けます。

| 判定 | 後続 | 扱い |
| --- | --- | --- |
| 直接寄与しない確認 (`[状態確認]`) | 問わない | Act に残し、呼び出し (`[手順]`) と判定を別の文に分ける |
| 被テスト関数の判定 (`[確認_*]`) | 有意な手順がある | Act に残し、呼び出しと判定を別の文に分ける |
| 被テスト関数の判定 (`[確認_*]`) | 有意な手順がない | Assert へ移す |
| ループの中の判定 | 問わない | Act に残し、呼び出しと判定を別の文に分ける |

Table: Act フェーズの中の ASSERT の扱い

有意な手順は、判定した呼び出しの結果 (戻り値、出力引数、状態) に依存する関数の呼び出しです。値を変数へ退避する文や後始末は含みません。`ASSERT_*` は失敗すると以降の処理を実行しないため、後続の手順の前提を守る判定は Act に残します。

```cpp
// Act
FILE *out = cplat_fopen(path.c_str(), "wb", nullptr); // [手順] - 書き出し先を開く。
ASSERT_NE(nullptr, out);                             // [状態確認] - cplat_fopen() の戻り値が nullptr 以外であること。
size_t wrote_mgmt = fwrite(mgmt, 1, mgmt_size, out); // [手順] - 管理領域を書き出す。
```

## Assert フェーズ [確認_*]

### 目的

このフェーズでは、テストの結果が期待どおりであることを確認し、テストの成功または失敗を判断します。

### 内容

- テスト対象のメソッドの戻り値を確認します。
- オブジェクトの状態が期待どおりであることを確認します。

### タグ

| タグ | 用途 |
|-----|------|
| `[確認_正常系]` | 正常な動作パスの確認 |
| `[確認_異常系]` | エラー処理パスの確認 |

Table: Assert フェーズの検証タグ一覧

Assert フェーズの各 `ASSERT_*` / `EXPECT_*` マクロには、検証内容と一対一に対応する `[確認_正常系]` または `[確認_異常系]` のコメントを付与します。  
後続の検証を継続できるか確認するための `ASSERT_*` マクロも、テスト結果の確認であるため省略しません。  
クラッシュしないことを示す場合は、コメントだけで済ませず `SUCCEED()` を記載して確認タグを付けます。

### Assert に置く文

Assert フェーズには、判定と、判定のための値の取り出しや集計だけを置きます。

| 文の種類 | Assert に置けるか | 例 |
| --- | --- | --- |
| 判定のマクロ (`EXPECT_*`、`ASSERT_*`、`SUCCEED()`) | 置ける | `EXPECT_EQ(3, verbose);` |
| 被テスト対象の状態を変えない宣言、代入、ループ、検索 | 置ける | ログから該当の行を探すループ、見つかったことを示すフラグ |
| 判定だけを行うサブ手順の呼び出し | 置ける | `testing::expectExportNamesMatch(expected, actual);` |
| 被テスト対象への操作 (`[手順]` を付ける呼び出し、書き込み、状態の変更) | 置けない (Act へ移す) | `memset(buf, 0xAB, 16U);`、`cplat_argparser_handle_parse(parser);` |

Table: Assert フェーズに置ける文

操作の結果を判定し、その後に別の操作を行う場合は、[マルチ フェーズ テスト](#マルチ-フェーズ-テスト) に分けます。

```cpp
// Act
buf = (uint8_t *)cplat_malloc(16U); // [手順] - 16 バイトを指定して cplat_malloc() を呼び出す。

// Assert
ASSERT_NE(nullptr, buf); // [確認_正常系] - cplat_malloc() の戻り値が nullptr 以外であること。

// Act_2
memset(buf, 0xAB, 16U); // [手順] - 確保した 16 バイト全体に 0xAB を書き込む。

// Assert_2
EXPECT_EQ(0xAB, buf[0]); // [確認_正常系] - buf[0] が 0xAB であること。
```

### 例

```cpp
// 戻り値が期待どおりであることを確認
ASSERT_TRUE(result); // [確認_正常系] - TestedMethod() の戻り値が true であること。

// オブジェクトの状態を確認
EXPECT_EQ(ExpectedState, state); // [確認_正常系] - state が ExpectedState であること。
```

### 確認コメントの書き方

確認タグ (`[確認_*]`、`[Pre-Assert確認_*]`、`[状態確認]`) の説明文には、マクロが行う判定をそのまま書きます。  
テストの手順と確認の説明は、製品コードのコメントと異なり、コードが何をしているかの直接的な説明を主体にします。  
`results.md` では説明文とテスト コードが並んで載るため、判定をそのまま書くと、読み手が説明文とマクロを突き合わせやすくなります。

説明文は、判定 (1 文目) と、必要な場合の総合期待で構成します。

```text
// [確認_正常系] - <判定>。(<総合期待>ことの確認)
```

- 判定は「〜であること。」などの形で書き、句点で終えます。
- 総合期待は、判定だけでは意図が読み取れない場合に書きます。判定の句点の直後に空白を入れずに半角の括弧で囲み、「〜ことの確認」で終えます。括弧の後に句点は付けません。
- 総合期待を書くのは、0 や 0 以外などの値の意味、期待値の数値の由来、比較の理由などを補う場合です。判定から自明な言い換え (戻り値が成功を表す値であることに対する「成功したことの確認」など) は書きません。

判定は、確認すべき値を主語にし、期待値とどのような関係かを簡潔に表します。主語は次のように書きます。

- 関数の戻り値は「f() の戻り値」と書きます (f は関数名)。戻り値を変数で受けてから判定する場合も、マクロの引数に関数呼び出しを直接書く場合も同じです。両辺が関数の戻り値の場合は、両辺とも「f() の戻り値」と書きます。「戻り値が true であること。」だけでは、テスト エビデンス上でどの手順の戻り値かを判別できません。
- メソッドの戻り値は、オブジェクト名を含めて書きます (例: 「results.size() の戻り値」)。
- テスト内のヘルパー関数を通して呼ぶ場合は、テストが呼ぶヘルパー関数の名前を書きます。
- 関数の戻り値以外 (出力引数、ループで作った変数、構造体のメンバーなど) は、変数名や式をそのまま書きます。
- 同じ関数を時点や入力を変えて呼び分けている場合は、その条件を主語の前に置きます (例: 「追加後の …」「nullptr の空入力に対する …」)。判定の対象を特定する引数 (探す文字列など) も、主語の前に置きます (例: 「"キューの長さは 7 です。" を探した captured.find() の戻り値が …」)。
- 関数名の後には `()` を付け、引数は書きません。
- 識別子と値はバッククォートで囲みません。
- 期待値の文字列リテラルは全文書きます。
- 期待値や引数条件に含まれるキャストのうち、型をそろえるためだけのものは省いて書きます (例: `static_cast<int>(sizeof(buf))` は「sizeof(buf)」、`(uint8_t)0xAB` は「0xAB」)。値の意味を変えるキャスト (符号の扱いを変える `(uint32_t)-1`、ポインターの同一性を比べる `(void *)` など) は残します。
- C++ のテスト コードの空判定は `nullptr` と比べ、「nullptr 以外であること。」「nullptr であること。」と書きます。空ポインターの表記の規則は [コーディング規範](../../../app/general/docs/coding-guideline.md) の「空ポインターの表記」に従います。

マクロごとの判定の書き方は次のとおりです。`ASSERT_*` は対応する `EXPECT_*` と同じです。

| マクロ | 判定の書き方 |
| --- | --- |
| `EXPECT_EQ(A, B)`、`EXPECT_DOUBLE_EQ(A, B)` | A が値 (リテラル、定数) なら「B が A であること。」、A が変数や式なら「B が A と一致すること。」 |
| `EXPECT_NE(A, B)` | B が A 以外であること。 |
| `EXPECT_LT(A, B)` / `EXPECT_LE(A, B)` | A が B より小さいこと。/ A が B 以下であること。A が期待値 (リテラル、定数) なら、B を主語にして「B が A より大きいこと。」/「B が A 以上であること。」 |
| `EXPECT_GT(A, B)` / `EXPECT_GE(A, B)` | A が B より大きいこと。/ A が B 以上であること。A が期待値なら、B を主語にして「B が A より小さいこと。」/「B が A 以下であること。」 |
| `EXPECT_TRUE(X)` / `EXPECT_FALSE(X)` | X が true であること。/ X が false であること。 |
| `EXPECT_STREQ(A, B)` / `EXPECT_STRNE(A, B)` | B が A であること。/ B が A 以外であること。 |
| `EXPECT_THAT(V, M)` | V が <M の意味> であること。(M は Pre-Assert フェーズの「マッチャーの言い換え」に従う) |
| `ASSERT_NO_THROW(S)` | S が例外を送出しないこと。(S が関数呼び出しなら「f() が例外を送出しないこと。」) |
| `ASSERT_NO_FATAL_FAILURE(f())` | f() の中で致命的な失敗が起きないこと。 |
| `EXPECT_NONFATAL_FAILURE(S, T)` | <S の内容> が T を含む非致命的な失敗を報告すること。 |
| `EXPECT_DEATH(S, R)` / `EXPECT_EXIT(S, P, R)` | f() がプロセスを終了させ、出力が R に一致すること。(`EXPECT_EXIT` は終了条件 P も書く) |
| `SUCCEED()` | SUCCEED() に到達すること。(直前の処理の意味は総合期待に書く) |
| `EXPECT_FILE_EXISTS(F)` | F のファイルが存在すること。 |
| `EXPECT_FILE_CONTAINS(F, T)` | F のファイルが T を含むこと。 |
| `Assert.Equal(A, B)` (.NET) | `EXPECT_EQ(A, B)` と同じ |
| `Assert.True(X)` / `Assert.False(X)` (.NET) | `EXPECT_TRUE(X)` / `EXPECT_FALSE(X)` と同じ |
| `Assert.Contains(A, B)` (.NET) | B が A を含むこと。 |
| `Assert.Throws<E>(S)` (.NET) | S が E を送出すること。 |
| `Assert.Null(X)` / `Assert.Same(A, B)` / `Assert.IsType<T>(X)` (.NET) | X が null であること。/ B が A と同じインスタンスであること。/ X の型が T であること。 |

Table: マクロごとの判定の書き方

```cpp
EXPECT_EQ(CPLAT_OK, actual_ret_added_table); // [確認_正常系] - 追加後の cplat_hashtable_get_table_generation() の戻り値が CPLAT_OK であること。
EXPECT_EQ(1u, added_table);                  // [確認_正常系] - added_table が 1 であること。(追加でテーブル世代が 0 から 1 増えたことの確認)
EXPECT_NE(0, actual_after_release);          // [確認_正常系] - actual_after_release が 0 以外であること。(解放後の出力で条件を取り込んだことの確認)
EXPECT_STREQ("a", buf);                      // [確認_正常系] - buf が "a" であること。(上矢印が無視されたことの確認)
```

### 状態と手順の説明文の表記

#### 共通原則

`[状態]`、`[手順]`、`[Pre-Assert手順]` の説明文は、次の原則に従います。文型を定める 4 種類 (注入、関数の呼び出し、既定動作、待機) 以外の説明文 (データの用意、値の書き込み、状態の変更など) は、この原則だけに従います。

- 文末を動詞の終止形 (「〜する。」) で終えます。
- 操作の対象を書きます。
- 関数名には、確認タグの説明文と同じく引数なしの `()` を付け、識別子をバッククォートで囲みません。
- 関数名は、コードで実際に呼んでいる関数の名前を書きます。関数名を動詞として使いません (「push() する」とは書きません)。

`[状態]` は、テストの開始時点で用意されている状態を書きます。関数を呼び出す `[状態]` にも、[関数の呼び出し](#関数の呼び出し-手順) の文型は適用しません。

```cpp
char buf[32];                     // [状態] - 出力バッファーを用意する。
ASSERT_EQ(0, compile("^b", &re)); // [状態] - パターン "^b" をコンパイルしておく。
```

#### 注入 ([Pre-Assert手順])

`[Pre-Assert手順]` は、動作を注入する関数の名前を必ず書き、「f() から」で始めます。

| 注入する動作 | 文型 | 例 |
| --- | --- | --- |
| 戻り値を返す | f() から X を返す。 | cplat_malloc() から nullptr を返す。 |
| 呼び出しごとに戻り値を変える | f() から 1 回目は X、2 回目は Y を返す。 | cplat_fgets() から 1 回目は "first"、2 回目は "second" を返す。 |
| errno や出力引数を設定して戻り値を返す | f() から、〜を設定して X を返す。 | send() から、errno に EPIPE を設定して -1 を返す。 |
| 何もせずに戻る (戻り値なし) | f() から戻る。 | cplat_console_init() から戻る。 |
| 動作を伴って戻る (戻り値なし) | f() から、〜して戻る。 | freeaddrinfo() から、渡された解決結果を確かめて戻る。 |
| 元の処理へ委譲する | f() から 1 回目は X を返し、以降は〈委譲先〉へ委譲する。 | cplat_malloc() から 1 回目は nullptr を返し、以降は製品 (prod) の処理へ委譲する。 |

Table: 注入の文型

動詞は「返却する」ではなく「返す」を使います。委譲先は、[モックの作成方法](how-to-mock.md) の「用語」の節の呼び方 (「製品 (prod) の処理」「libc の処理」など) で書きます。

```cpp
EXPECT_CALL(mock_unistd_, fsync(_, _, _, kFakeFd))
    .WillOnce(Return(0)); // [Pre-Assert確認_正常系] - fsync() が kFakeFd を指定して 1 回呼び出されること。
                          // [Pre-Assert手順] - fsync() から 0 を返す。
```

> [!NOTE]
> `results.md` の手順節には、`[手順]` と `[Pre-Assert手順]` の説明文だけが並んで出力されます。関数名がないと、どの関数がどの値を返すかを手順節だけでは判別できません。確認タグの「f() の戻り値」と同じく、関数を明記します。

#### 関数の呼び出し ([手順])

文の主な操作が関数の呼び出しである `[手順]` (戻り値を変数で受ける文を含む) は、文末を「f() を呼び出す。」とし、テストの観点となる引数や状態を「〜を指定して」「〜の状態で」の形で前に置きます。引数をすべて列挙する必要はありません。

```cpp
int result = cplat_tracer_write_at(handle, CPLAT_TRACE_LEVEL_INFO, nullptr,
                                   "test message"); // [手順] - INFO レベルと "test message" を指定して cplat_tracer_write_at() を呼び出す。
int actual_ret_push = potr_internal_window_send_push(&win, &pkt); // [手順] - 満杯のウィンドウに 5 件目のパケットを指定して potr_internal_window_send_push() を呼び出す。
```

代入やループなど、関数の呼び出しでない `[手順]` は [共通原則](#共通原則) に従います。

#### 既定動作 ([状態] の ON_CALL)

`ON_CALL` の `[状態]` は、既定動作の内容を「注入」の節の文型で書き、「ように既定動作を設定する。」を続けます。

```cpp
ON_CALL(mock_cplat, cplat_isatty(_)).WillByDefault(Return(0)); // [状態] - cplat_isatty() から 0 を返すように既定動作を設定する。
ON_CALL(mock_stdlib_, atexit(_, _, _, _))
    .WillByDefault(Invoke(delegate_real_atexit)); // [状態] - atexit() から libc の処理へ委譲するように既定動作を設定する。
```

> [!NOTE]
> `ON_CALL` は Arrange に置くため状態節に出力され、`[Pre-Assert手順]` の注入値とは別の節に出ます。既定動作の内容を書いても、注入値と並んで矛盾して読まれることはありません。

#### 待機

プロセスの出力や終了を待つ説明文は、関数の呼び出しの文型の例外とし、「〈プロセス〉が〈出力〉を出力するまで待機する。」「〈プロセス〉が終了するまで待機する。」と書きます。

```cpp
bool actual_ret_wait_hello =
    tryWaitForOutput(recv_h_, "Hello Porter", 3000); // [手順] - RECIEVER が "Hello Porter" を出力するまで待機する。
```

> [!NOTE]
> 待機の関数はテストの進行を合わせる手段で、読み手にとっての要点はどのプロセスの何を待つかです。説明文とコードの対応は、確認タグ (「"Hello Porter" を待つ tryWaitForOutput() の戻り値が true であること。」) で取れます。

#### 説明文の空ポインターの表記

C++ のテスト コードでは、エビデンス タグの説明文 (`[状態]`、`[手順]`、`[Pre-Assert手順]`、確認タグの判定、条件、総合期待) の空ポインターを一律「nullptr」と書きます。C で書かれた製品コードの振る舞いを説明する場合も同じです。

```text
key に nullptr を指定して cplat_hashtable_get() を呼び出す。
handle が nullptr であること。(cplat_tracer_dispose() がハンドルを nullptr にしたことの確認)
```

#### 記号の文字そのもの

説明文で記号の文字そのもの (波括弧など) を指す場合は、二重引用符で囲みます。エスケープ シーケンスは、C の文字列リテラルの形で二重引用符に入れて書きます。

```text
対を成さない "}" を含む書式を指定して cplat_internal_string_catalog_render_text() を呼び出す。
dest が "value={ 123 }" であること。("{{" と "}}" が 1 文字の波括弧になったことの確認)
"\x1B[1~" を指定して test_pinned_prompt_read_key() を呼び出す。
```

> [!NOTE]
> `text_style_jp.py` は、コメント中の二重引用符で囲んだ部分を整形の対象から外します。引用符の外にある単独の括弧は、文字そのものか括弧かを機械的に判定できず、括弧の内側の空白を除く整形の対象になります。

## Cleanup フェーズ

### 目的

テストで確保または変更したリソースや状態を、Assert フェーズの完了後に元へ戻します。

### 内容

- 確保したメモリやハンドルを解放します。
- テストで作成したファイルやディレクトリを削除します。
- テストで変更したグローバル状態を復元します。

- Cleanup フェーズは任意であり、明示的な後処理がある場合だけ、その直前に `// Cleanup` を記載します。
- 明示的な後処理がない場合は、空の `// Cleanup` を記載しません。
- 終了系 API 自体の挙動を試験する呼び出しや、結果を確定するために必要な終了操作は Act フェーズへ記載します。
- fixture の `TearDown`、ヘルパー内の後処理、RAII による自動解放には、テスト本体の `// Cleanup` を記載しません。
- Cleanup フェーズの解放や復元の操作には、テスト エビデンス用のタグを付けません。
- Cleanup フェーズ内で後処理の呼び出し期待を `EXPECT_CALL` に登録する場合も、`[Pre-Assert確認_*]` を付け、期待の検証 1 回を 1 件として集計します。登録位置を変更すると先行する呼び出しとの照合が変わる場合があるため、件数対応だけを目的に移動しません。

### 例

```cpp
// Assert
EXPECT_TRUE(result); // [確認_正常系] - TestedMethod() の戻り値が true であること。

// Cleanup
remove(outputPath);
```

4 つの必須フェーズと、必要な場合だけ Cleanup フェーズを順番に記載することで、テスト コードの役割を明確に区別できます。

## シングル フェーズ テストとマルチ フェーズ テスト

テスト コードは、Arrange→Pre-Assert→Act→Assert のサイクルを 1 回だけ含む **シングル フェーズ テスト** と、同じサイクルを 1 つのテスト関数内に複数回含む **マルチ フェーズ テスト** のいずれかとして記載します。状態遷移や複数ステップの手続きを 1 テストで検証する場合は、マルチ フェーズ テストを使用します。

### シングル フェーズ テスト

- `// Arrange` `// Pre-Assert` `// Act` `// Assert` `// Cleanup` に番号を付けません。ここまでの節で説明した記法がこれにあたります。

### マルチ フェーズ テスト

- 1 回目のサイクルの構造コメントには番号を付けません。2 回目以降のサイクルで、実際に繰り返す構造コメントにだけ `_N` を付与します (`// Arrange_2` `// Pre-Assert_2` `// Act_2` `// Assert_2`)。番号は 2, 3, 4 ... とテスト全体を通して単調増加する連番です。
- **部分反復を許容します**。4 つの構造コメントすべてが揃うサイクルの反復だけでなく、特定のフェーズだけを複数回繰り返すことができます。
    - 例: `// Arrange` → `// Pre-Assert` → `// Act` → `// Act_2` → `// Act_3` → `// Assert` のように、Act だけを複数回行い、最後に 1 回だけ Assert で確認するシナリオです。
    - この場合、`// Arrange` `// Pre-Assert` `// Assert` は 1 回しか出現しないため番号を付けません。`// Act` の 2 回目以降にだけ `_2` `_3` を付けます。
- 4 つの構造コメントは、テスト全体を通してそれぞれ 1 回以上存在することを必須とします。個々のサイクル (番号) ごとに 4 つすべてが揃っている必要はありません。
- `// Cleanup` には番号を付与しません。各サイクルの Assert 直後に、そのサイクルで確保したリソースだけを解放する書き方と、全サイクル完了後にまとめて 1 回だけ解放する書き方のどちらでも、`// Cleanup` は番号なしのまま使います。エビデンス整理ロジックは `// Cleanup` をサイクル境界の判定対象に含めず、意味のある処理としても扱いません。
- ブラケット タグ (`[状態]` `[状態確認]` `[Pre-Assert確認_*]` `[Pre-Assert手順]` `[手順]` `[確認_*]`) には番号を付けません。どのサイクルに属するかは、直近に出現した構造コメントの番号から自動的に判定されます。

### サイクル境界の判定ロジック

エビデンス整理ロジックは、`// Arrange` `// Pre-Assert` `// Act` `// Assert` のいずれかの構造コメントを検出するたびに、その番号 (省略時は 1) がそれまでの最大値を超えていれば、その番号を現在のサイクルとして更新します。超えていなければ現在のサイクルは変わりません。

例 (Act だけの部分反復):

```text
// Arrange       → 現在サイクル 1
// Pre-Assert    → 現在サイクル 1
// Act           → 現在サイクル 1 (以降のタグはサイクル 1)
// Act_2         → 現在サイクル 2 に更新 (以降のタグはサイクル 2)
// Act_3         → 現在サイクル 3 に更新 (以降のタグはサイクル 3)
// Assert        → 番号 1 は現在サイクル 3 を超えないため更新なし (タグはサイクル 3 のまま)
```

### エビデンス出力

シングル フェーズ テストでは `### 状態` / `### 手順` / `### 確認 (正常系:n1, 異常系:n2)` を番号なしで出力します。

マルチ フェーズ テストでは、サイクルごとに次の形式を連続して出力します。

```text
### 状態_N

### 手順_N

### 確認_N (正常系:n1, 異常系:n2)
```

## テスト エビデンス (results.md)

`make test` を実行すると、各テスト ケースごとに `results.md` が生成されます。

### 出力先

```text
<テストディレクトリ>/results/<TestSuite>.<TestName>/results.md
```

**例**:

```text
app/sample/test/src/libsampleTest/sampleCloseTest/results/sampleCloseTest.handle_null/results.md
```

### ファイル構成

`results.md` は、先頭のテスト ID、判定、実施日時に続いて、次の 3 節で構成されます。  
コメントがある場合は備考を記載します。実行コマンドは実行結果節に記載します。

```text
# <TestSuite>.<TestName>

- 判定: PASSED
- 実施日時: 2026-10-11 10:00:00 JST

## テスト項目の詳細

<テスト項目サマリー>

## テスト コード

<cpp または csharp のコード ブロック>

## 実行結果

<実行コマンドと出力の text コード ブロック>
```

概要とタグがないテストでは、テスト項目の本文を「なし」とします。  
状態節 (状態_N を含む) の本文が空の場合は「特記すべき状態なし」、手順節と確認節の本文が空の場合は「なし」とします。確認件数合計は見出しに値を示すため、本文はありません。  
エビデンス生成が失敗した場合は判定を FAILED とし、テスト項目に `> [!CAUTION]` でエラーを記載します。

すべての結果ファイルは BOM なしの UTF-8、LF 改行で出力し、末尾を改行 1 つで終えます。  
コード ブロックのフェンスは、内容中の最長のバッククォート連続より 1 つ長い長さとし、最低 3 個とします。  
テスト名とファイル名はインライン コードにせず、Markdown の記法として解釈される文字だけをバックスラッシュでエスケープします。  
実行結果の ANSI エスケープ シーケンスはファイルから除去します。

#### 実施日時はローカル時刻で記載する

日時の形式は `YYYY-MM-DD HH:MM:SS <時刻帯>` です。時刻帯は `date '+%Z'` の値を使います。  
日本語の Windows で `TZ` が未設定の場合、Git for Windows などの `date` は `%Z` を空白だけで出力します。このときは UTC からの差 (`%z`、例: `+0900`) を時刻帯として記載します。  
この判定は `bin_internal/local_time.sh` と、.NET 向けの `parse_trx_results.py` が行います。  
C/C++ の個別結果は、そのテストのバイナリを起動する直前に `local_time.sh` で取得します。エビデンス生成に失敗したテストにも実施日時を記載します。  
.NET の個別結果は TRX の `startTime` を `date -d '<startTime>'` で同じ形式に変換します。Theory は属性を持つレコードの最も早い時刻を使い、どのレコードにも属性がない場合は一括実行を開始した時刻を使います。  
個別結果とパラメーター テストの各レコードでは判定の直後に実施日時を置きます。定義単位ファイルの先頭のメタデータは変更せず、実行レコード節に各レコードの実施日時を記載します。  
全体サマリーの実施日時は全テストの開始時刻です。コンソールの `Test start on <date>.` の表示は変えません。

#### テスト項目

テスト コード内のコメント タグからテスト エビデンスが自動生成されます。

`TEST` / `TEST_F` / `TEST_P` / `TYPED_TEST` の直前に空行を挟まず書いた `//` コメントが、概要 (description) になります。複数行でも構いません。`TEST_F(Suite, name)` では、この前置コメントと第 2 引数 `name` が対になります。識別子だけを概要の代わりにはしません。直前に空行があると、それより前のコメントは取り込まれません。

説明コメントを先に、サブ手順参照を後に書き、テスト定義との間に空行を挟みません。  
概要の収集では、テスト定義より前の参照行と展開範囲を読み飛ばします。空行、参照以外のタグを含むコメント、コメント以外の行では、それまでの概要を破棄します。

```text
## テスト項目の詳細

<TEST_F 直前の // コメント>

### 状態        ← [状態] タグから生成
### 手順        ← [手順] / [Pre-Assert手順] タグから生成
### 確認        ← [状態確認] / [確認_*] / [Pre-Assert確認_*] タグから生成 (件数も集計)
```

各節の中の項目は、テスト コード上の記載順をもとに、フェーズの順「テスト本体の前 → Arrange → Act → Pre-Assert → Assert → テスト本体の後」で並べます。  
同じフェーズの中は、テスト コード上の記載順です。  
Pre-Assert に書くモックの期待と動作は Act の実行中に働くため、Act の項目の後に並べます。  
並び順は記載位置から決め、実行時の呼び出し順は記録しません。  
最初のフェーズ コメントより前の項目は Arrange に、`// Cleanup` より後の項目は直前のフェーズに属します。  
サブ手順に由来する項目の入れ子と親項目は、[サブ手順](test-subprocedures.md) を参照してください。

#### テスト コード

テスト コードそのもの (コメント含む) が記録されます。  
2 行以上連続する空行は、由来を問わず 1 行にまとめて掲載します。

### プラットフォーム条件分岐

C/C++ のテスト エビデンス生成では、テスト本体内にある Linux と Windows の条件分岐を実行環境に応じて評価し、有効な分岐だけをテスト項目サマリーと元のテスト コードに出力します。

Linux では `PLATFORM_LINUX` と `__linux__`、Windows では `PLATFORM_WINDOWS` と `_WIN32` を定義済みとして扱い、他方を未定義として扱います。  
これらのマクロ `X` の単独判定として、`#if defined(X)`、`#elif defined(X)`、`#if !defined(X)`、`#elif !defined(X)`、`#ifdef X`、`#ifndef X` を評価します。テスト本体とサブ手順には同じ規則を適用します。  
`#` の前後、ディレクティブ名の後、括弧の内側、`!` と `defined` の間の空白を許容します。

```cpp
#if defined(PLATFORM_LINUX)
    // Linux で出力するテスト コード
#elif defined(PLATFORM_WINDOWS)
    // Windows で出力するテスト コード
#else
    // どちらのマクロも定義されていない場合のテスト コード
#endif
```

単一のプラットフォームだけを対象とする場合は、`#if defined(PLATFORM_LINUX)` または `#if defined(PLATFORM_WINDOWS)` と `#endif` を組み合わせます。

```cpp
#if defined(PLATFORM_LINUX)
    // Linux で出力するテスト コード
#endif
```

```cpp
#if defined(PLATFORM_WINDOWS)
    // Windows で出力するテスト コード
#endif
```

対応する条件分岐は、入れ子にしても実行環境に応じて評価されます。  
無効な分岐を除いて生じた連続する空行は、テスト コード節では 1 行にまとめます。

次の書式はプラットフォーム条件として評価されません。

- 対象外のマクロ (`WIN32`、`_WIN64`、`linux`、`LINUX` など) を含む条件
- `&&` または `||` を含む複合条件
- 条件式の後ろにコメントなどのトークンを置く書式

対応していない書式ではプラットフォームによる絞り込みを行わず、プリプロセッサ ディレクティブを含めて抽出します。

`TEST`、`TEST_F`、`TEST_P` などのテスト定義全体を囲む条件分岐は評価対象ではありません。

同名のテストをプラットフォームごとに重複定義すると各定義が連結して抽出されるため、テスト本体を一つにして、本体内の差異だけを対応する条件分岐で記載します。

#### gtest 実行結果

`[ RUN ] / [ OK ] / [ FAILED ]` などの Google Test の出力が記録されます。

### タグと出力の対応

| タグ | テスト項目への反映 |
|-----|-------------------|
| `[状態]` | `### 状態` セクションに箇条書きで列挙 |
| `[状態確認]` | `### 確認` セクションに `- (説明文)` の形式で列挙 (件数には計上しない) |
| `[手順]` / `[Pre-Assert手順]` | `### 手順` セクションに列挙 |
| `[確認_*]` / `[Pre-Assert確認_*]` | `### 確認` セクションに列挙・件数集計 |

Table: テスト タグとサマリー出力セクションの対応

> [!NOTE]
> タグの直後に箇条書きの説明文を続けることで、サマリーに説明が出力されます。通常は ` - <説明文>` と記載します。
> 確認タグには箇条書きの説明文を付けます。確認件数は箇条書きの項目数ではなく、タグに指定した回数から集計します。

> [!NOTE]
> 確認タグのカテゴリ、回数式、説明文に不備がある場合はエラーにします。状態や手順のタグは完全一致で抽出します。

> [!NOTE]
> マルチ フェーズ テスト ([シングル フェーズ テストとマルチ フェーズ テスト](#シングル-フェーズ-テストとマルチ-フェーズ-テスト) 参照) では、`### 状態` `### 手順` `### 確認` の見出しに `_N` が付与され、サイクルごとに分離して出力されます。

### [状態確認] を含む出力例

```cpp
// Arrange
char *buffer = (char *)malloc(16); // [状態] - 16 バイトのバッファーを確保する。
ASSERT_NE(nullptr, buffer); // [状態確認] - buffer が nullptr 以外であること。

// Pre-Assert

// Act
int actual_ret = sample_func(buffer); // [手順] - 確保したバッファーを指定して sample_func() を呼び出す。

// Assert
EXPECT_EQ(SAMPLE_OK, actual_ret); // [確認_正常系] - sample_func() の戻り値が SAMPLE_OK であること。
```

```text
### 状態

- 16 バイトのバッファーを確保する。

### 手順

- 確保したバッファーを指定して sample_func() を呼び出す。

### 確認 (正常系:1)

- (buffer が nullptr 以外であること。)
- 【正常系】sample_func() の戻り値が SAMPLE_OK であること。
```

`[状態確認]` の 1 件は見出しの `(正常系:1)` に含まれず、`[確認_正常系]` の 1 件だけがカウントされます。

## 確認のカテゴリ分類

### 概要

`[確認]` および `[Pre-Assert確認]` タグに `_正常系` または `_異常系` のサフィックスを付けると、確認件数をカテゴリ別に集計できます。

**サフィックスは必須** とし、サフィックスなしの `[確認]` / `[Pre-Assert確認]` は使用しません。

カテゴリを省略した確認タグは解析エラーになります。

### カテゴリの判断基準

| カテゴリ | 目安 |
|---------|------|
| `_正常系` | 機能が正常に動作することを確認する (成功パス・通常の動作) |
| `_異常系` | エラー処理や入力不正への対応を確認する (失敗パス・防御処理) |

Table: テスト検証カテゴリの判断基準

### 確認項目の区分表示

`[確認_正常系]` と `[Pre-Assert確認_正常系]` に由来する項目には `【正常系】`、`[確認_異常系]` と `[Pre-Assert確認_異常系]` に由来する項目には `【異常系】` を付けます。  
区分は箇条書きの記号の直後に置き、区分と説明文の間に空白を入れません。回数の表記は項目の末尾に付けます。  
`[状態確認]` は従来どおり説明文を括弧で囲み、区分を付けません。サブ手順の親項目にも区分を付けません。  
サブ手順の子項目は、件数集計と同じ区分を表示します。参照に `区分` 属性がある場合は指定を反映し、入れ子では内側の指定を優先します。  
区分のない確認タグは解析エラーになるため、区分のない確認項目は出力されません。

### 集計結果の表示

カテゴリ タグを 1 つでも使用すると、テスト結果のサマリーが分類別に表示されます。

```text
### 確認 (正常系:n1, 異常系:n2)
```

0 件のカテゴリは表示されません。

サフィックスなしの `[確認]` / `[Pre-Assert確認]` は解析エラーになります。

**例**: 正常系 2 件・異常系 1 件の場合

```text
### 確認 (正常系:2, 異常系:1)
```

## 期待を確認する行為 1 回を 1 件として集計する

確認件数は、テスト設計上、期待を確認する行為の回数です。  
`ASSERT_*` / `EXPECT_*` や .NET の Assert は、対応する期待を確認する実行 1 回を 1 件とします。  
`EXPECT_CALL` は一つの呼び出し期待を 1 件とし、`.Times(3)` は「3 回呼ばれるという期待」で 1 件、`.Times(0)` も「呼ばれないという期待」で 1 件です。  
ループで独立した呼び出し期待を 3 個登録する場合は 3 件になります。  
`[状態確認]` は集計対象外です。

確認タグの「個数」はソース上の記載箇所の数で、「確認件数」は各確認タグの回数式を評価した合計です。両者は区別します。  
実行環境によって個数が変わる確認 (errno の一覧など) は、期待する一覧と実際の一覧を 1 回で照合するなど、実行環境によらず確認回数が一定になる形にします。  
ループ全体の説明と、ループ内の各判定の説明が重複する場合、全体の説明はタグを付けない通常のコメントにします。

作成者は、アルゴリズムとテスト データから、各確認の実施回数を決定して記載します。  
集計処理は `for` や `if` の実行回数を推測しません。  
テスト本体外の確認を含める場合は、[サブ手順](test-subprocedures.md) として定義し、テストから参照します。  
SetUp・TearDown はテストの直前・直後に空行を挟まず参照を置き、共通関数は呼び出し箇所に参照を付けます。  
Assert の失敗、例外、途中の `return` などによる実測回数の変化も反映しません。

### 回数は確認タグの内側に記載する

```cpp
// [確認_正常系] - actual が expected と一致すること。
// [確認_正常系 回数=1] - actual が expected と一致すること。
// [確認_正常系 回数=2+3] - actual が expected と一致すること。
// [確認_異常系 回数=PARAM*(2+3)] - func() の戻り値が ERR であること。
// [Pre-Assert確認_正常系 回数=PARAM*2*3] - notify() が 1 回呼び出されること。
```

回数 1 回だけは `回数=1` を省略できます。  
省略時は、通常テストでもパラメーター テストでも、テスト全体で 1 回です。  
各レコードで 1 回ずつ確認する場合は `回数=PARAM` を明記します。  
回数指定は `[確認_正常系]`、`[確認_異常系]`、`[Pre-Assert確認_正常系]`、`[Pre-Assert確認_異常系]` に共通です。  
確認タグには `-`、`*`、`+` または番号付きリストで始まる説明文を付け、期待確認一つに対して確認タグを一つ記載します。

回数式には半角の非負整数、予約語 `PARAM`、加算 `+`、乗算 `*`、括弧 `()` を使用します。  
式内の空白を許可し、乗算を加算より先に評価します。  
減算、除算、符号、任意の変数名、関数呼び出しは使用しません。

```text
式   := 項 ("+" 項)*
項   := 因子 ("*" 因子)*
因子 := 非負整数 | "PARAM" | "(" 式 ")"
```

`回数=0` は、対象のテスト データではその確認を実施しないことを表します。  
カテゴリなし、不明なカテゴリ、回数指定の重複、説明文の欠落、不正な式は解析エラーになります。

### 回数式はテスト全体の確認回数を表す

「テスト全体」は一つのテスト定義に属する全パラメーター レコードを指します。  
通常テストではテスト関数 1 回分です。  
同じ `TEST_P` を複数の `INSTANTIATE_TEST_SUITE_P` で登録した場合も、そのテスト定義に属するレコードを合算します。  
`PARAM` はテスト ランナーが展開したレコード数を表し、各レコード内のパラメーターの列数ではありません。  
通常テストで `PARAM` を使用するとエラーになります。

数値だけの指定も全体合計です。  
3 レコードのループ回数がそれぞれ 1、2、4 回の場合は `回数=1+2+4` と記載します。  
5 レコードのうち正常系の分岐を 3 レコード、異常系の分岐を 2 レコードが通る場合は、それぞれ `回数=3`、`回数=2` と記載します。  
式全体にパラメーター数を暗黙に掛ける処理は行いません。

```cpp
for (int i = 0; i < 3; ++i) {
    EXPECT_EQ(expected[i], actual[i]); // [確認_正常系 回数=3] - actual[i] が expected[i] と一致すること。
}
```

### テスト定義ごとにサマリーを一度だけ生成する

C/C++ のパラメーター テストは、定義単位の `results/<Suite>.<Test>/results.md` と、レコード単位の `results/<Suite>.<Test>/<Prefix>/<Param>/results.md` を生成します。  
定義単位のファイルは全レコードの終了後に書き出し、総合判定、判定別の実行レコード数、テスト項目、テスト コード、実行レコードを記載します。総合判定は FAILED、WARNING、PASSED の順に優先します。  
実行レコードの節には判定、実施日時、レコードへの相対リンク、実行結果だけを記載します。レコードのテスト項目は定義単位への相対リンクとし、全体件数を重複掲載しません。  
.NET はメソッド単位にまとめます。構造コメントの番号に従ってサイクル別・カテゴリ別に加算し、複数サイクルがあれば全体合計も表示します。

レコード数は、C/C++ では Google Test の展開済みテスト一覧、.NET では TRX のレコード別結果から取得します。  
`InlineData` の行数やソースのカンマ数からは推測しません。  
レコード数を確定できない場合、`PARAM` を含む式は解析エラーにします。  
フィルターで一部レコードだけ実行した場合は、全体用の回数式をそのまま集計せず、全体の確認件数を「未評価」と表示します。

```text
### 確認 (正常系:12, 異常系:2)

- 【正常系】値が一致すること。〔12 回: PARAM*3、PARAM=4〕
- 【異常系】エラーが返ること。〔2 回〕
```

明示した回数式は、説明文の後ろに計算結果とともに出力します。  
省略した 1 回は従来の説明文だけを出力します。  
サブ手順に由来する項目は、1 以外の回数だけを表示します ([サブ手順](test-subprocedures.md) を参照)。  
解析処理は任意のコードを実行せず、トークン化と再帰下降解析で式全体を検証します。  
エラーにはテスト識別子と抽出コード内の行番号を添え、サマリー生成失敗を実行スクリプトの失敗として扱います。

## 全体サマリーの確認件数

`results/all_tests/summary.md` は、全テストの開始時刻を示す実施日時、テスト対象ソースの MD5、テスト結果、集計、確認件数、警告とエラー、カバレッジを記載します。  
MD5 とカバレッジは C/C++ で生成した場合だけ、警告とエラーは該当がある場合だけ記載します。  
テスト結果と確認件数のテスト ID は、対応する結果ファイルへの相対リンクにします。  
各表には、表の直後に [表のキャプション](../../docsfw/docs/table-caption.md) の `Table:` 行で表題を付けます。

確認件数の表は、テスト定義ごとに正常系、異常系、計を記載し、末尾に合計行を設けます。  
通常テストは 1 テストで 1 行、C/C++ のパラメーター テストは定義単位で 1 行、.NET はメソッド単位で 1 行です。行順はテスト結果で定義が最初に現れる順とします。  
確認タグがない定義も 0 件の行を記載し、定義がない場合は「なし」とします。  
回数式とサブ手順の参照回数を反映した、個別結果と同じ集計値を使用します。`[状態確認]` は件数に含めません。

一部レコードだけを実行したパラメーター テストと、テスト項目サマリー生成に失敗したテストは「未評価」とし、合計から除外します。  
該当がある場合は、表のキャプションの下に「合計には、未評価のテスト定義 <n> 件を含みません。」と記載します。  
確認件数は管理目的でファイルに記録し、コンソールには追加しません。
